# 日次バッチ高速化計画(2026-09-04)

## 0. 制約

**取得元のレート制限を超えないこと。** 本計画は「並列度を上げて速くする」もの
ではない。後述のとおり、実効HTTPレートは**下げつつ**所要時間を約70%短縮する。

## 2. 実測したリクエスト本数(yfinance 1.4.1、`YfData._make_request` を計数)

| 経路 | リミッター acquire | 実HTTPリクエスト |
|------|------------------|----------------|
| `fetch_raw_financials` | 1 | **6**(quoteSummary×1 + fundamentals-timeseries×5) |
| `fetch_latest_price` | 1 | **2**(chart×1 + timeseries×1) |
| `YfinanceConsensusProvider.fetch` | **0** | **2**(quoteSummary×2) |

### 2.1 判明した事実:設定値 `yfinance_requests_per_second: 2.0` は実レートを表していない

`_throttle()` は**呼び出し単位**で acquire する(`yfinance_client.py` の
docstring もそう明記している)が、1回の呼び出しが最大6本のHTTPを出す。

実測から逆算した 2026-09-02 の実効レート:

- collection: 5,799銘柄 / 7,316秒 = 0.79銘柄/秒
  → acquire **1.59/秒**(上限2.0の79%)、実HTTP **6.34 req/秒**
- consensus: 5,889銘柄 / 6,732秒 = 0.875銘柄/秒
  → acquire **0/秒(リミッターを通っていない)**、実HTTP **1.75 req/秒**
- 日次yfinance総本数: 5,799×8 + 5,889×2 = **58,170本**

つまり **collection は名目上限の約3.2倍のHTTPレートで既に走っている**。
「並列度を上げる」案は、この時点で全て却下される——実効6.34 req/秒は
Yahooが現に許容している水準(失敗30/5,799 = 0.5%)だが、上限として
**設計されたものではなく偶然そうなっている**だけであり、上乗せする根拠が無い。

したがって速くする手段は**本数を減らすこと**に限られる。

## 3. 施策

### S-1. リミッターをHTTP単位にする(**前提条件。他の施策より先**)

`_throttle()` を呼び出し単位から**実HTTPリクエスト単位**へ移す
(`YfData._make_request` を1箇所でラップする)。そのうえで
`yfinance_requests_per_second` を **6.0** に設定し直す。

- 意味論の変更ではなく**是正**である。現状「2.0」は何も表していない。
- 6.0 は現に毎日持続している 6.34 req/秒 を**わずかに下回る**値。
  すなわちピークレートは今より下がる。
- これが入って初めて、以降の並列化が「上限を超えない」ことが構造的に保証される
  (今は上限が効いていないので、並列度を上げれば青天井になる)。

### S-2. 財務諸表の取得を週次に降格(collection: 122分 → 約46分)

`fetch_raw_financials` の6本のうち **5本は fundamentals-timeseries**、すなわち
四半期に1度しか変わらない財務諸表である。これを毎日5,799銘柄ぶん取り直している。

**同じ判断は既にこのリポジトリで下されている**——`xbrl_facts` 工程は
「財務データなので四半期に1回しか変わらない。週次で足りる」を理由に週次に
なっている(`daily_pipeline.py`)。yfinance側の財務諸表だけが日次のまま残っていた。

- 日次: `info`(1) + `history`(1) + `get_shares_full`(1) = **3本/銘柄**
- 週次(月曜): 財務諸表5本を追加取得
- 日次本数: 46,392 → **17,397本(−62%)**

**この施策の唯一の危険:`raw_snapshots.payload` の形が崩れること。**
`apply_gates.py` は `raw.payload` から `balance_sheet` /
`quarterly_cash_flow` / `quarterly_income_stmt` を読む。`available_from <=
snapshot_date` の**最新1件**を取るので、財務諸表を欠いた行が最新になると
ゲートが静かに壊れる(`api/routes.py:1228,2787` と `run_monitoring.py:113`
も同じ payload を読む)。

→ **必須の実装条件**:財務諸表を取得しない日は、直近の
`raw_snapshots.payload` に入っている財務諸表を**そのまま持ち越して**保存し、
payload の形を日ごとに変えない。持ち越し元が無い銘柄(新規)はその日に
財務諸表も取得する。

### S-3. consensus の `.info` 取得を廃止(consensus HTTP本数を半減)

`YfinanceConsensusProvider.fetch` は2本のうち1本(`.info`)を
**`targetMeanPrice` 1項目のためだけ**に投げている。同じ銘柄の同じ `info` は、
数時間前に collection 工程が取得して `raw_snapshots.payload["info"]` に
保存済みである。DBから読めば **5,889本/日が丸ごと消える**。

### S-4. consensus を共有リミッター配下で並列化(112分 → 約16分)

現状 `collect_consensus` は `for ticker in query.all():` の**完全な逐次ループ**で、
`run_parallel` も使っておらず、**リミッターも通っていない**。1.75 req/秒しか
出ていないのはレート制限のせいではなく、単に直列だからである。

S-1 と S-3 の後であれば、5,889本を 6.0 req/秒で流して約16分。
**S-1 より先にこれをやってはいけない**(上限が効いていない状態で並列化すると
そのままレート超過になる)。

### S-5. EDGAR系工程の並列化(litigation 19分 → 約4分)

`litigation` / `filing_sections` / `dilution` / `customer_concentration` は
いずれも銘柄ごとの逐次ループ。litigation は299銘柄で3.8秒/銘柄=実質0.26 req/秒
であり、設定上限 `edgar.requests_per_second: 5.0` の**5%しか使っていない**。

共有 `sec` リミッター配下で並列化する。上限を触る必要は無い——余っている枠を
使い切るだけであり、5.0 req/秒(SEC公表上限約10の半分)はそのまま。

**実装前に確認すること**:`EdgarClient` が共有リミッターを
**HTTPリクエストごとに**通しているか。通していなければ S-1 と同じ是正を先に行う。

### S-6. macro_exposure のクエリ折り畳み(13分 → 1分未満、ネットワーク無関係)

`collect_macro_exposure` の内側ループが、**全銘柄について同じ4本のFRED系列を
毎回フルスキャンし直している**:

```
for ticker in tickers:          # 299
    for factor in factors:      # 4
        session.query(MacroSeries)...  # ← 全履歴を再取得。全銘柄で同一の結果
```

299×4 = 1,196回の全系列クエリ。さらに `observation_end` の計算で
`_weekly_last(prices)` を factor ループの中で毎回再計算している。

- 4本の系列取得と `_returns` 変換を**ticker ループの外へ括り出す**(1,196 → 4)
- `_weekly_last(prices)` を ticker ごとに1回だけ計算して使い回す

純粋な計算の重複であり、出力は1ビットも変わらない。

## 5. 実装順序(依存関係があるため厳守)

1. **S-1**(リミッターのHTTP単位化)— 他の全ての前提
2. **S-6**(macro_exposure)— 独立・ネットワーク無し・最も安全。先に入れて回帰が無いことを確かめる
3. **S-3**(consensus の `.info` 廃止)— 本数削減。並列化より先
4. **S-4**(consensus 並列化)— S-1 と S-3 の後
5. **S-2**(財務諸表の週次化 + 持ち越し)— 最も慎重を要する。payload 持ち越しのテストを厚く
6. **S-5**(EDGAR並列化)— 独立。最後でよい

## 6. やってはいけないこと

- `max_workers` や `yfinance_requests_per_second` を、**S-1 を入れないまま**
  引き上げること。上限が実レートを表していない状態での引き上げは、
  そのままレート超過になる。
- `request_jitter_*` を 0 にすること。ジッタは送信パターンを崩すためのもので、
  レート上限とは別の役割(`rate_limit.py` docstring)。並列化で得られる分を
  ジッタ削除で稼ぐ必要は無い。
- サーキットブレーカーの闕値・`min_sample_size` を緩めること。速度と無関係。
- consensus の対象母集団(5,889銘柄)を絞ること。PIT履歴の網羅性に関わる
  データ方針の変更であり、高速化の名目で混ぜてよい変更ではない。

## 7. S-7. 決算通過をトリガーにした財務諸表の即時再取得(2026-09-04追記)

S-2(財務諸表の週次格下げ)を実データで検証した結果、無視できない副作用が
見つかった。

### 7.1 実測(2026-09-02〜、約2週間の観測)

- **日次の内容一致率:99.75%。** 財務諸表を毎日取り直しても、ほとんどの
  銘柄・ほとんどの日は前日と1バイトも変わらない同一内容を再送していた。
  S-2の「週次で足りる」という前提は大筋で正しい。
- **一方、観測された統計諸表の全変化220件のうち75件(34%)が非月曜日に
  発生していた。** これらはS-2の週次化により、最大6日(平均4.8日)
  `apply_gates`への反映が遅れる。
- **ゲート対象(≒スコアが実際に使われる)銘柄に絞っても13銘柄が、この
  観測期間中に影響を受けた。** 母数(数千銘柄)からすれば小さいが、遅延が
  発生する銘柄は無作為ではない——**決算発表が非月曜日の統計諸表変化の
  主因であり、決算は「今まさにスコアが動くべき」瞬間そのもの**である。
  週次化の恩恵(HTTP本数−62%)を保ったまま、この一番痛いケースだけを
  狙い撃ちする価値がある。

### 7.2 設計

`event_calendar`(J-6、293銘柄ぶんの次回決算日)を参照し、決算日を過ぎた
ティッカーは週次日を待たず財務諸表を再取得する(`snapshot_collector.py`の
`_earnings_triggered_refetch`)。設計上の要点3つ:

1. **「財務諸表を実際に取得した日」をどこに記録するか。** マイグレーション無しの
   方式を採った——`raw_snapshots.payload`に`_statements_as_of`
   (取得した`snapshot_date`のISO文字列)を常設キーとして追加し、持ち越し時
   (`_carry_forward_statements`)はこれも**上書きせずそのままコピー**する。
   `payload`の形(キー集合)を変えないというS-2の不変条件をそのまま守れ、
   消費者(`apply_gates.py`等)は未知キーを無視するので後方互換も保たれる。
   代替案(`tickers`に列を足す)はマイグレーションが要るため見送った——
   本タスクの実施時点で本番の`run-daily-pipeline`が`collection`工程を
   実行中であり、Alembicマイグレーションはロック競合のため適用できない
   (適用するまで機能しない「書いたが使えない」状態を避けた)。
2. **猶予窓(既定3日、`statement_refresh_grace_days`)が必要な理由。**
   yfinanceのfundamentals-timeseriesは決算発表の反映に通常1〜2日ラグが
   ある。決算日当日1回だけの再取得だと、発表前の未更新値を掴んだまま
   終わってしまう——決算通過をトリガーにする目的そのものが骨抜きになる。
   決算日(E)から猶予窓の最終日(E+grace_days)までは、yfinance側がまだ
   決算を反映していなくても**毎日再取得を試み続ける**ことで、反映後の
   値をいつ捕まえても取りこぼさない。
   **2026-09-04監査で発見した欠陥**:初版の実装は「最後に取得した日が
   決算日そのものより前かどうか」で判定していたため、決算日当日に1回
   fetchした瞬間、猶予窓の残り日数を無視してその決算については「取得
   済み」扱いになっていた——`grace_days`をいくつにしても猶予窓が実質
   1回で終わる、まさにこの2番目のポイントが防ぐはずだった失敗モードを
   再現する欠陥だった。正しくは「最後に取得した日が猶予窓の**終わり**
   (`event_date + grace_days`)より前かどうか」で判定する(修正済み、
   回帰テストあり)。
3. **自己収束すること。** `event_calendar`は次回決算日を保持するテーブルで、
   決算日を過ぎても`events`工程(週次)が次の日付に更新するまで過去日の
   ままになる。単純に「決算日を過ぎていれば毎日再取得」にすると、次の
   月曜が来るまで**毎日**再取得し続け、S-2の効果を自ら打ち消す。
   「決算日から`grace_days`日以内」というクエリ条件そのものが収束点を
   決めている——猶予窓を過ぎると対象の決算が検索条件にヒットしなくなり
   (`latest_relevant_event_date is None`)、そこでぴたりと止まる
   (テストで確認済み)。

### 7.3 コスト試算

1日あたり決算日を迎えるティッカーは293銘柄 ÷ 四半期91日 ≒ 5件。それぞれ
猶予窓の間(既定4日=当日+3日)は毎日再取得を試みるため、ある1日に
「猶予窓の中にいる」ティッカーは重複込みで高々20〜25件、1銘柄5リクエスト
(財務諸表5本)なので**日次+100本程度**。S-2適用後の基準(17,397本/日)の
1%に満たず、無視できる増分である。

`event_calendar`に行が無いティッカー(追跡対象外の大多数)はこの施策の
対象外——週次のみのままで、これは意図した挙動である(タスク仕様どおり
カバレッジは広げない)。

### 8.3 なぜcollectionだけ見込みを外したか(正直な記録)

§4の見込み(collection −62%)はS-2(財務諸表の週次格下げによるHTTP本数
削減)だけを根拠にしていた。**本数を減らせばレート上限(6.0 req/秒)に
張り付いている時間が減り、その分だけ速くなるという前提**だったが、
これは前提が誤っていた——collectionは実際にはレート上限に張り付いて
いなかった。

実測(5,799銘柄、`max_workers: 5`のまま):

- collection: 5,799銘柄 / 6,139秒 = 0.945銘柄/秒。1銘柄3リクエスト
  (S-2適用後:`info`+`history`+`get_shares_full`)なので実HTTP
  **2.83 req/秒——天井6.0の47%しか使えていない**。
- consensus: 5,889銘柄 / 1,023秒 = 5.76銘柄/秒 = 5.76 req/秒
  ——天井の**96%**。

同じ`max_workers: 5`・同じ天井6.0 req/秒なのに稼働率が47%と96%に
分かれた理由は、`run_parallel`(collectionが使う実行経路)が銘柄ごとに
1〜3秒(平均2.0秒)のジッタを挟むのに対し、`collect_consensus`の
Executor(S-4で追加)にはジッタが無いこと。ジッタの分だけワーカー1本の
占有時間が延び、ワーカー5本という頭数がレートより先に律速していた。

**つまりS-2は「本数を減らす」ことには成功したが、collectionの律速要因を
レート上限から本数(=ワーカー数)へ移しただけで、その移った先を
そのままにしていた。** 見込みが外れたのはS-2の設計ミスではなく、
S-2が効果を発揮するための前提(ワーカー数がレートより先に律速しない
こと)を検証せずに置いていたため。これがS-8で埋める。

## 9. S-8. 収集ワーカー数の引き上げ(2026-09-04、実測を受けて)

8.3で確認した通り、collectionは天井6.0 req/秒の47%しか使えておらず、
律速しているのはワーカー数(5)である。yfinance系2ステージのうち
**collectionだけ**に伸びしろが残っている(consensusは96%で天井に
既に張り付いている)。

### 9.1 サイジングの算数

- ワーカー1本あたりの占有時間:5ワーカー ÷ 0.945銘柄/秒 = **5.29秒/銘柄**
  (ジッタ平均2.0秒 + 実処理時間相当)。
- 天井6.0 req/秒を使い切るスループット:3 req/銘柄なので **2.0銘柄/秒**。
- 必要ワーカー数:2.0銘柄/秒 × 5.29秒/銘柄 ≈ **10.6 → 10**に切り上げ。

`config/collection.yaml`の`max_workers`を**5 → 10**に変更した。

### 9.2 なぜ2026-08-23の事故(並列8で30.1%失敗)と矛盾しないか

`config/collection.yaml`の`max_workers`直上のコメントに残っている
2026-08-23の実データ検証(並列8・ジッタ0.5〜2.0秒で478銘柄処理時点に
transient_failureが144件=30.1%、サーキットブレーカー作動)は**削除せず
そのまま残した**。この記録と「並列8で壊れたのに10は安全と言えるのか」
という当然の疑問に、コメント内で直接答えている。

要点:2026-08-23時点では**リミッターが実HTTPレートを制限していなかった**。
`_throttle()`は`fetch_raw_financials`等の**呼び出し単位**でしかacquireせず、
1回の呼び出しが最大6本のHTTPを出していたため(§2)、ワーカー数がそのまま
実HTTPレートに掛かっていた——並列8は文字通りYahooを洪水攻撃していた。

S-1(本計画・実装済み)でリミッターを実HTTPリクエスト境界
(`YfData._make_request`)へ移して以降は、**ワーカー数を増やしても実HTTP
レートは`yfinance_requests_per_second`(6.0)を超えられない**。ワーカー数が
埋めるのは「天井の下で空いている時間」だけであり、天井そのものは
ワーカー数と無関係に効き続ける。したがって2026-08-23の事故は
「リミッターが機能していない状態で並列度を上げると危険」という教訓を
示しているのであって、「並列度そのものが危険」だったわけではない——
S-1後の現在はその前提条件(リミッターが機能していない状態)が解消されている。

さらに、`max_workers: 10`で見込まれる実効レート(約5.67 req/秒、天井の
94%)は、**2026-09-03以前に数週間にわたって日次で持続していた
6.34 req/秒(失敗率0.5%)より低い**。つまりこれは未検証の負荷水準への
踏み込みではなく、既にYahooが日常的に許容していた水準を下回る範囲での
引き上げである。

### 9.3 consensusとの共有について

`max_workers`は`collect_consensus`(S-4)とも共有されている設定値である。
consensusは既に実効5.76 req/秒(天井の96%)まで使い切っており、ここに
ワーカーを増やしても待ち時間が減らない(レート自体が変わらないため)。
したがって**この変更の効果はcollectionにのみ生じ、consensusの所要時間は
変化しない見込み**——両方が同じ設定値でスケールすると誤解しないこと。

### 9.5 DB接続プールの明示化

`max_workers`引き上げに伴い、`src/autoscreener/db/session.py`の
`create_engine`にSQLAlchemyの未宣言の既定値(`pool_size=5,
max_overflow=10` → 合計15接続)を暗黙に頼る状態を解消した。

collection/consensus(`collection.max_workers: 10`)とEDGAR系
(`edgar.max_workers: 10`)はいずれもワーカー1本につきDBセッション1本を
保持しうるため、1ステージあたり最大で約11接続(ワーカー10 +
呼び出し元スレッド分1)を必要とする。`daily_pipeline.py`はステージを
逐次実行するため実際に同時に必要になるのはどれか1ステージぶんだけだが、
「暗黙の既定値にたまたま収まっていた」状態を終わらせるため、
`pool_size=20, max_overflow=10`(合計30接続、必要数11の約3倍)を
明示した。どちらかの`max_workers`を今後さらに引き上げる際は、この
プールサイズも合わせて見直す前提とする(コメントに明記)。
